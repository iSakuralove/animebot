# 0003. 不用 FTS5，用 LIKE + rapidfuzz

状态: 已采纳
日期: 2026-09-05

## 背景

1639 个帖子要做中文检索。SQLite 自带 FTS5，Python 3.12 的内置 sqlite
（3.45.1）已编译 `ENABLE_FTS5=1`。直觉上「全文检索就该用全文索引」。

## 决策

**普通表 + `LIKE '%kw%'` 预筛 + 打分函数精排 + rapidfuzz 兜底。** 不建 FTS5 虚表。

## 理由

### FTS5 的 trigram tokenizer 对中文 2 字查询是废的

实测（[_scratch 里的探测脚本](../../src/animebot)已删，数据留在这里）：

```
标题: "无职英雄 ～技能什么的毫无用处～"  tokenize='trigram'

match '英雄'      -> 0   未命中
match '无职'      -> 0   未命中
match '技能'      -> 0   未命中
match '无职英雄'   -> 1   命中
match '毫无用'     -> 1   命中
```

trigram 要求查询至少 3 个字符。而「搜两个汉字」是最常见的用法
（`鬼灭`、`咒术`、`英雄`）。

`unicode61` + 逐字空格切分能命中 2 字查询，但代价是要维护一个影子列
（把标题拆成 `无 职 英 雄`），加上触发器保持同步 —— 凭空多一层一致性问题。

### LIKE 在这个数据量上根本不是瓶颈

实测 1639 行 / 70 万字符：

| 查询 | 全文 LIKE | 仅标题 LIKE |
|---|---|---|
| `英雄` | 3.49ms（34 命中） | 0.49ms（9 命中） |
| `无职英雄` | 2.98ms | 0.61ms |
| `少女` | 2.84ms（511 命中） | 0.42ms（100 命中） |

rapidfuzz 对 1447 个标题做模糊排序：**10.5ms**。

所以完整一次搜索 13ms 以内。架 FTS5 换来的是 3ms → 0.3ms，
代价是影子列 + 触发器 + 一致性风险。

### 数据量的天花板很远

标题总量 70 万字符。SQLite 全表扫的成本随数据线性增长，到 10 万个帖子
（当前 60 倍）时 LIKE 大约 200ms —— 那时候才该重新考虑。而这个频道
四年半发了 1639 个帖子。

## 代价

**放弃了相关性排序（BM25）。** FTS5 自带按词频/文档频率排序，我们得自己写
`rank()` 打分函数。但这反而是好事：我们要的排序规则是「精确 > 前缀 > 标题中间 >
别名 > 正文」，加上「同层级短标题优先」，这套业务规则 BM25 表达不出来。

**放弃了词组查询语法**（`"a b" NEAR/5 c`）。用户不会用这个。

**这个决策在什么时候失效**：帖子数超过 5 万，或者出现「必须按相关性排序的长文本
搜索」需求。届时的迁移路径是加一张 FTS5 影子表，`SearchService` 换一个
`_candidates()` 实现 —— 调用方和打分逻辑不用改，因为候选获取已经隔离在
`repo.like_titles()` / `repo.like_fulltext()` 后面了。
