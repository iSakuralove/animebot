# 0010. 分页状态编进 callback_data，不放服务端

状态: 已采纳
日期: 2026-09-05

## 背景

`#漫改` 有 572 个帖子，`少女` 有 109 条。一页 8 条，必须分页。

分页需要在按钮点击时知道「哪个查询、第几页」。Telegram 的 `callback_data`
上限 64 **字节**（不是字符），而中文一个字 3 字节。

三种存法：

| 方案 | 代价 |
|---|---|
| 查询词编进 callback_data | 长查询超限 |
| 服务端存结果集，callback 只带 session id | 内存增长、失效策略、重启丢失 |
| 服务端只存查询词，不存结果 | 同上但内存小得多 |

## 决策

**默认把查询词直接编进 `callback_data`（`s:<page>:<query>`）。超过 64 字节时
退到短 token + 进程内有界 LRU（`t:<page>:<8位token>`）。**

翻页时重新查库重新排序，**不缓存结果集**。

## 理由

**实测绝大多数查询塞得下。** `s:13:少女` 是 11 字节，`s:71:#漫改` 是 12 字节。
19 个汉字以内都能内联 —— 番名通常 2~10 字，标签组合 30 字节左右。

内联的好处是**无状态**：重启不失效、不需要清理、不占内存、多实例部署也不用
共享状态。

**但超限不是假想。** 库里就有这个标题：

```
英雄王，为了穷尽武道而转生～而后，成为世界最强的见习骑士♀～
30 个汉字 = 90 字节
```

用户直接粘贴标题搜索就会超。所以必须有退路，而不是截断查询词（那会返回错误
结果，比报错更糟）。

**不缓存结果集**，因为实测一次完整检索只要 12~35ms（最坏是 `#漫改` 572 条
全排序 34ms）。缓存要处理失效、内存增长、以及「翻页时帖子被编辑了」的一致性
问题。省 20ms 不值这些复杂度。

前提是排序确定：`sort_key` 是全序（先命中词数，再匹配质量），重新查得到的
顺序完全一致。有测试断言翻页不重复不漏项。

## 代价

**`QueryStore` 是进程内的，重启丢失。** 用户点旧消息的翻页按钮会看到「搜索
已过期，请重新搜索」。可接受：可恢复、有明确提示、而且只影响超长查询这条
冷路径。

**LRU 淘汰同样会导致过期。** 容量默认 512，按每次搜索最多 1 个 token 算，
要 512 次超长查询才会淘汰最早的。真实使用中几乎不可能触发。

**多实例部署会让 token 路径失效** —— A 实例存的 token，B 实例查不到。但项目
本来就是单实例（见 [ADR-0009](0009-single-instance-lock.md)），且内联路径不受
影响。真要多实例时把 `QueryStore` 换成 Redis 实现即可，接口不变。

**每次翻页都重新查库。** 用户快速连点翻页会产生多次查询。当前延迟下无所谓，
但如果哪天单次检索涨到 200ms+，就该重新考虑缓存了 —— 那个信号会先在
`search.latency` 埋点上出现。

## 什么时候这个决策会失效

- 单次检索延迟超过 ~100ms（届时缓存的收益开始超过复杂度）
- 需要多实例部署（token 路径需要外部存储）
- 需要在翻页时保持「搜索时刻的快照」语义（当前是每次读最新数据）

前两个有明确的迁移路径，第三个需要真的缓存结果集 —— 但目前没有任何需求指向它。
