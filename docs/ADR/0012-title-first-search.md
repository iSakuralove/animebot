# 0012. 默认搜标题，全文只在标题零命中时回退

状态: 已采纳
日期: 2026-09-19

## 背景

`/s 青春` 把两种命中混在一起返回：

1. 标题里有「青春」的番（用户想要的，3~5 条）
2. 简介 / staff 里提到「青春」的番（噪音，几十条）

用户打「青春」的本质意图是「**有没有叫青春的番**」——这是对标题的查询。把简介
命中混进来既不符合心智，又把结果撑到几十条、触发翻页。

旧实现（[service.py](../../src/animebot/search/service.py) 的 `_rank_all`）是一条
**隐式级联**：先搜标题，`if len(候选) < 一页` 就自动追加全文候选一起排。这个
「不足一页就扩」的判断，恰恰在标题命中少（3~5 条 < 8）时触发，于是标题命中
永远被全文命中稀释——正是最该保持干净的场景反被污染。

## 决策

**拆成显式两路，`title_only` 开关控制：**

| 入口 | 模式 | 行为 |
|---|---|---|
| 私聊纯文本 | `title_only=True` | 只搜标题；零命中走 fuzzy 纠错，**不碰全文** |
| `/s <词>`（任意场景） | `title_only=False` | 标题优先；标题**零命中才**回退全文，带提示行 |

- **标题命中非空时，绝不混入全文命中**（对比旧的「不足一页就扩」）。
- 回退用 **A 方案**：标题零命中才回退，顶部一行提示
  `没匹配到标题，以下是"青春"相关内容：`，让用户知道这批不是标题命中。
- 「标题」= `search_blob` = 中文名 + 英文名 + 别名（`repo.like_titles`），
  不含简介 / staff / 标签。搜 "Mushoku" 命中英文名算标题命中。

`search()` / `search_page()` / `/check` / CLI 的默认值是 `title_only=False`，
行为不变（`/check` 本来就该能靠简介找到）。

## 理由

**这同时是「慢」的解，不只是相关性的解。** 一个被反复误解的前提先钉死：
**检索没有网络查询**，数据全在本地 SQLite，10~28ms。用户感知的「慢」是
Telegram 投递消息的往返（~350ms/次走代理），翻页每次都要一次往返。老架构
「一点即达」不是因为它静态，而是因为它**搜完发一条就结束，只有一次往返**。

标题命中天然就少（实测）：

| 查询 | 全文命中 | 仅标题 |
|---|---|---|
| 青春 | 几十条 | 3~5 |
| 无职英雄 | 1 | 1 |
| 进击的巨人 | 4 | 4 |

**标题结果少 → 一条消息装得下 → 不翻页 → 一次往返 → 老架构的手感回来。**
所以「默认搜标题」一箭双雕：既对齐意图，又消掉翻页往返。这才是用户说的
「静态架构」的真正含义——不是预生成、不是绕开 SQLite（查询才 10ms，不是
瓶颈），而是**让默认路径的结果少到不需要翻页**。

**纯文本只在私聊触发。** 群里 catch 所有消息会把每句闲聊当搜索，是灾难。
群里搜索必须显式 `/s`，所以群里不注册纯文本 handler。

**为什么是 A 方案（零命中才回退）而不是「标题命中 + 全文命中都给、分区展示」？**
后者又把结果撑多、又要设计分区 UI、又回到翻页往返。A 方案保持默认路径
「结果少、一次往返」的核心收益，只在标题真没有时才多花一次全文查询。

## 代价

**标题命中被标签滤光时要继续回退。** `#校园 英雄` 标题命中 `[无职英雄,
英雄教室]`，`#校园` 过滤后只剩 `英雄教室`——如果过滤把标题命中滤没了，全文
模式应当继续回退，不是空手而归。所以判空放在**标签过滤之后**
（`_ranked_over` 先过滤再返回，`_rank_all` 判空）。这消掉了「过滤前判空」
会漏掉的一个特殊情况。

**多一个 `title_only` 参数要一路透传。** search_page → SearchPage → 翻页
callback → decode → search_page。漏传任何一环，翻页会按错误模式重查、结果集
变了导致翻页串位。所以模式位编进了 callback_data（见
[ADR-0010](0010-pagination-state-in-callback-data.md) 的格式扩展），并有
`test_mode_bit_roundtrips_*` 盯着往返。

**fuzzy 纠错在两种模式下都不算「回退」。** 它是标题域的错别字容错（见
[ADR-0008](0008-fuzzy-on-title-only.md)），`fell_back` 恒为 False，所以标题
模式打错字仍能纠错、但不会弹「相关内容」提示。

## 什么时候这个决策会失效

- 如果哪天出现「标题命中太多也需要翻页」的真实场景（某个两字词标题命中
  50+），默认路径的「一次往返」收益就没了——但那时该做的是更精准的标题排序，
  不是回到混全文。
- 如果用户反馈「我就是想连简介一起搜」成为高频诉求，才考虑给纯文本入口也加
  一个显式的全文开关（比如 `/s!` 或按钮）。目前没有需求指向它。
