# 0013. 漫画频道接入：频道是数据，一个库、一个解析器，channel_id 当作用域

状态: 已采纳
日期: 2026-10-24

## 背景

要加 `/c` 搜第二个频道「ACG Library 二次元图书馆」（id `1659887654`）。
2026-10-24 的导出：1257 条消息、938 个帖子、271 条文件消息（整卷压缩包）。

代码当时假设只有一个频道：`Settings.channel_id`、`ChannelSync.accepts()`、回填的
频道校验都只认动漫频道，而且**仓储的检索查询根本不带频道条件** —— 直接把漫画
导出灌进同一个库，`/s` 立刻会搜出漫画帖。

两个频道的数据关系（实测）：

- 同一个 up 主：网盘账号 `yxhmbookshare`、解压密码 `blackcatunderthemoon` 两边都有。
- 同一套模板家族：`中文名`/`别名`/`作者`/`话数`/`评分`/`引索`/`标签`/`故事简介`
  两边都用；动漫频道甚至转发过几条漫画/轻小说帖（#963、#1396 就是漫画频道的帖子）。
- 现成解析器直接跑漫画导出：937 个有效帖、1 个 FAILED。追查那个 FAILED（#555）
  发现旧解析器其实一直在给它造假标题 —— 它通篇没有中文名，旧代码把第二行
  `发售日: 2012-06-04` 当成了标题。

## 决策

1. **频道是数据。** `config.Channel(key, title, channel_id, username)`，
   `Settings.channels = (anime, manga)`。同步、回填、启动自检、`/health`、
   `/syncstat` 都遍历它，不认具体是哪个频道。
2. **一个 SQLite 库，`channel_id` 是检索作用域。** 仓储的检索方法（`like_titles`、
   `by_tags`、`all_titles`、`tag_cloud`）`channel_id` 是**必填**关键字参数；
   `SearchService` 构造时绑定一个频道（默认动漫）。统计方法（`count`、
   `status_breakdown`）`channel_id=None` 表示全库合计。
3. **一个解析器、一张别名表。** 漫画的写法（`发售日`、`连载开始`、`作画`、`册数`、
   `链接`…）带出现次数加进 `fields.py`，和动漫的写法放在一起。
4. **文件消息单独一张表 `channel_files`，归属读的时候现算**：文件属于
   「message_id 不大于它的、最近的那个有效帖子」。
5. **翻页按钮每个频道一套前缀。** 动漫 `s:`/`t:`/`x`（老格式，原样不动），
   漫画 `c:`/`ct:`/`cx`。
6. **`/c` 走宽松模式**（标题优先，零命中 fuzzy 纠错），纠错出来的结果在列表头
   标明「名字相近」。

## 理由

**为什么一个库而不是两个。** 数据结构早就是多频道的：主键是
`(channel_id, message_id)`，`post_tags`、`sync_state` 都按频道分。缺的只是查询
上的那个条件。两个库意味着两条连接、两套 closer、CLI 要维护「频道 → 文件」的
映射、handler 里出现 `repo` 和 `manga_repo` 两个名字。一个库的话，「那个频道」
这个特殊情况直接消失，变成一个参数。

**为什么检索方法的 channel_id 是必填的。** 漏传作用域不会报错，只会让结果悄悄
混进另一个频道的帖子 —— 这类错误只能靠「写不出来」来防。测试里两个频道各放
一部同名作品、同名标签（`test_channels.py`），任何串台都会被看见。

**为什么共用一张别名表，不做「每频道一套解析配置」。** 两个频道是同一个人按
同一套习惯写的。拆成两份配置，等于把「这个 up 主怎么写帖子」这份知识复制成
两份，然后看着它们漂移。动漫的黄金回归测试守着动漫不退化 —— 实际结果是动漫
这边也变好了（同一份导出，改前 vs 改后）：

| 变化 | 帖子 |
|---|---|
| `STORY` 简介头被认出，原本 SKIPPED（搜不到）的帖子变 PARTIAL | 5（#151 朝花夕誓、#163、#264、#269、#327） |
| 「链接：pan.baidu…」这类行不再被当噪音丢掉，帖子多出网盘链接 | 4（#246、#706、#1396、#2103） |
| 简介不再吞进「链接：…」行、空简介被补上 | 7 |
| 别名续行（`别名: Deep Sea` 下一行 `深海之驭海人`） | 1 |

**为什么文件归属读时现算。** 真实数据：271 个文件分给 90 个帖子，零孤儿，文件名
和帖子标题逐个对得上（`[諫山創][進擊的巨人(第8集)]…` 紧跟在「进击的巨人」后面）。
如果写入时就存归属，回填（遍历消息时记住「当前帖子」）和增量（查库找前一个帖子）
是同一条规则的两份实现。读时一条 SQL：规则只有一处；帖子被编辑成公告、公告被
编辑成帖子，归属自动跟着变。

**为什么加新前缀而不是给 callback 加一个「频道」字段。** 已经发出去的动漫翻页
按钮（`s:3:l:青春`）还躺在用户的聊天记录里，部署之后还会被点。改格式会让它们
全部失效；加前缀是纯增量。占位按钮也分开（`x` / `cx`），两个模块谁也不依赖对方
被加载。

**为什么 `/c` 宽松。** 动漫有两个入口（私聊纯文本宽松、`/s` 严谨），漫画只有
`/c` 一个。唯一的入口必须容错（`进击巨人` → 进击的巨人）。代价是纠错结果可能
「沾边但不是」—— 所以列表头写明「没有标题包含这个词，下面是名字相近的」，不冒充
命中。

**为什么不把文件 copyMessage 给用户。** 资源是频道成员的福利（ADR-0011 默认
internal 深链就是这个语义）。替用户转发文件等于把 bot 变成对非成员的分发器，
而且要求 bot 是频道管理员。现在的做法是给一个跳到第一个文件的深链（`📦55个文件
10.8GB`），成员一点就到，非成员点了是加入页 —— 和帖子本身的可见性一致。

## 代价

- 以后加的任何检索方法都得带 `channel_id`。这是刻意的摩擦。
- 文件归属是启发式：如果 up 主先发 B 的资料帖、再补发 A 的文件，文件会算到 B
  名下。现有数据里 0/271 次。
- `file_stats` 对每个文件跑一次相关子查询找主人。271 个文件亚毫秒级；文件数涨到
  几万时改成写入时存归属（`owner` 列 + 回填后批量重算）。
- 导出里没有漫画频道的 username，没配 `ANIMEBOT_MANGA_CHANNEL_USERNAME` 时
  public 模式下漫画链接也是 `/c/` 内部链接。启动自检会把真实 username 打进日志。
- 一张别名表意味着：将来为漫画加的某个写法，理论上可能改变某个动漫帖的解析。
  防线是两份黄金数据集都要绿。

## 什么时候这个决策会失效

- 接入一个**不是这个 up 主**、模板完全不同的频道 —— 那时才值得引入「每频道一套
  解析配置」。
- 单频道帖子数到 ~5 万：见 [design/search-optimization.md](../design/search-optimization.md)。
