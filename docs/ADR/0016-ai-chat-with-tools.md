# 0016. `/q` AI 对话：Claude 协议 + 自带工具 + 草稿流式

状态: 已采纳
日期: 2026-10-29

## 背景

要一个能回答「进击的巨人在 bangumi 上评分多少」这类问题的入口。关键在
**评分、排名、新番这类信息模型记不住也记不准**，所以它必须能查：Bangumi
（结构化元数据）、网页（时效性信息）、我们自己的频道索引（发过没有）。

网关（happycoding.xyz）实测的三条硬事实：

1. **只支持 Claude 协议**（`/v1/messages` + SSE）。也开了 `/v1/responses`，
   但那是 OpenAI 的形状，和 `tools` / `tool_result` 的语义不一样。
2. **模型强制 thinking**，传 `thinking: {type: disabled}` 直接 400。thinking
   块**不能回流**给下一轮（同样 400），而模型每轮都会产出它。
3. **服务端工具被静默丢弃**：请求里放 `web_search_20250305` 不会报错，
   也不会联网，模型会回答「我没有联网能力」。客户端工具（`tool_use` /
   `tool_result`）正常。

## 决策

**Claude 协议 + 自己实现工具循环 + 三个本地工具。**

| 工具 | 数据源 | 为什么必须是我们做 |
|---|---|---|
| `bangumi_search` | `api.bgm.tv/v0/search/subjects` | 评分会变，模型记忆必然过期 |
| `bangumi_detail` | `/v0/subjects/{id}` | 「这部讲什么」要简介和制作人员，模型会编 |
| `bangumi_browse` | 同一搜索接口的 filter | 「今年有什么穿越番」没有片名可搜，只能按条件列榜 |
| `web_search` | Bing HTML | 网关丢服务端工具，只能自己搜完回灌 |
| `channel_search` | 本地 SQLite（复用 `SearchService`） | 这是我们独有的数据 |

`bangumi_browse` 暴露的是 Bangumi 自己的 filter 语法（`tag` / `air_date` /
`rating` / `rating_count` / `rank`），不是我们造的 DSL。三个实测坑写进了工具描述
里，让模型自己避开：

- `limit` 服务端硬顶 20，传 100 也只回 20；
- `sort=score` 会把「1 人打 10 分」的冷门条目顶到第一 —— 按评分排序时强制
  加 `rating_count >= 300`（除非调用方自己给了更严的 `min_votes`）；
- `sort=rank` 会把未排名条目（`rank=0`）排在最前 —— 给 `max_rank` 时强制
  加 `rank >= 1`。

**流式用「占位消息 + 原地 edit」。** 先发一条「🤔 正在思考…」，生成过程中按
1.4 秒节流 `editMessageText` 它，结束时把最终文本 edit 进去。

试过 `sendMessageDraft`（Bot API 9.5），**放弃了**：它画的是临时草稿，
会和最终 `sendMessage` 在客户端**同时可见**，要等 30 秒自己过期才消失 ——
上线当天就被反馈「bot 回了两条一样的消息」。而且它只支持私聊。

edit 方案没有这些问题：一条消息从头长到尾，私聊和群里的 ephemeral 都成立。

**Markdown → Telegram HTML，不用 MarkdownV2。** MarkdownV2 要求转义 18 个
字符，模型漏一个整条消息 400；HTML 只需转义 `& < >`，解析失败还能退回纯文本
再发一次。

**主模型失败降级到兜底模型**，但只在**第一个 token 之前**。已经吐字了再换
模型，用户会看到两段文风不同的回答拼在一起。

## 理由

- **不用官方 anthropic SDK。** 需要的能力只有「把 SSE 的 text_delta 抽出来」，
  而工具循环、取消、超时、埋点本来就得自己写。多一个 SDK 多一份依赖和一套
  它自己的超时语义，换不来什么。
- **工具结果以 JSON 字符串回灌。** 模型对结构化输入更稳；出错时返回
  `{"error": ...}` 而不是抛异常 —— 一次工具失败不该让整轮对话崩掉。
- **工具轮数有上限（默认 4）**，到上限的最后一轮**不传 tools**，逼模型用已有
  信息收尾。直接截断会让用户拿到半个答案。
- **会话键是 `(chat_id, user_id)`。** 群里两个人同时问不该看到对方的上下文；
  私聊里两者相等，一套键覆盖两种场景。
- **上下文按条数截断且从「纯文本 user 消息」起头。** Claude 协议要求
  user/assistant 交替且以 user 起头，从 `tool_result` 处截断会 400。

## 代价

- **草稿是临时的。** 用户会看到草稿消失、正式消息出现的那一下跳变；如果生成
  超过 30 秒还没结束，草稿会先过期消失。这是平台语义，改不了。
- **每次回答至少 2 次 API 往返**（草稿 + 正式消息），加上工具轮次实际 4~8 次。
  实测一次带工具的回答 3~8 秒；纯聊天 2~4 秒。
- **网关的 thinking 必须付钱**。思考 token 也算 `max_tokens`，所以
  `ai_max_tokens=2000` 里可能有一半花在思考上。调到 8000 会被截断。
- **Bing 是手工解析 HTML。** 它改版就失效，而且可能返回人机验证页 ——
  `parse_bing` 解析不到时返回空列表，模型会说「没查到」而不是崩。
  DDG 在 VPS 上直接返回验证页，所以没选它。
- **会话在内存里，重启就没了。** 不做持久化：清理、迁移、多群隔离的复杂度
  换不来什么，用户重问一次就行。
