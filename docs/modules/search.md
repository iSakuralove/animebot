# search —— 检索与展示

两个文件：[service.py](../../src/animebot/search/service.py) 出结果，
[presenter.py](../../src/animebot/search/presenter.py) 排版。

分开是因为「怎么算相关性」和「怎么显示」变化频率完全不同 —— 前者半年不动，
后者随时在调。

## 三层管线

```
"#奇幻 无职英雄"
  ↓ Query.parse        拆出 tags=['奇幻'] terms=['无职英雄']
  ↓ 逐词 LIKE 预筛     并集，最多 search_max_candidates 条
  ↓ rank_terms 精排    (命中词数, 匹配质量) 两级排序
  ↓ 标签过滤
  → list[SearchHit]
```

预筛用 SQL（快但粗），精排用 Python（慢但准）。候选集上限 200，所以精排
永远只对 ≤200 个对象打分。

## 为什么必须逐词拆

`/s 无职 转生` 整串 `LIKE '%无职 转生%'` 命中 **0 条** —— 因为帖子里没有
「无职 转生」这个连续子串。逐词拆开后各自命中 1 条和 3 条。

这不是优化，是「多词搜索」这个功能能不能用的前提。

## 打分：一个函数取代多路分支

`rank()` 按精确度分层，每层给一个基础分：

| 层级 | 分数 | 例子（查 `无职`） |
|---|---|---|
| `exact` | 1000 | 标题就是「无职」 |
| `prefix` | 900 − 标题长度 | 「无职英雄～技能什么的…」 |
| `title` | 800 − 位置×2 − 长度×0.1 | 「转生成无职的我」 |
| `alias` | 700 − 位置 | 英文名或别名里命中 |
| `body` | 500 | 简介/staff 里命中 |
| `fuzzy` | ≤400 | 错别字容错，见下 |

同层级里减去标题长度和命中位置：**短标题、靠前命中优先**。
「无职英雄」比「某某某无职某某某某某」更可能是用户想要的。

`_FUZZY_SCALE = 4.0` 把 0~100 的 WRatio 映射到 0~400，**天花板压在 `body` 层
之下** —— 任何真实子串匹配都排在模糊匹配之前。这条不能破，否则用户搜到
的第一条是"猜"出来的。

## `sort_key` 为什么是元组

```python
return (-self.hits, -self.score)
```

先比命中词数，再比匹配质量。**不硬压成一个数。**

压成一个数就必须编一个权重（`hits * 10000 + score`），而那个权重是拍脑袋的，
调它等于调一个没人理解的魔数。元组排序的语义是明确的：命中 2 个词的结果
永远排在命中 1 个词的前面，不管分数多少。

## 模糊匹配的触发条件

**只在子串匹配零结果时触发。** 有任何真实命中就不走模糊 —— 模糊结果混进
正常结果里会让排序变得不可解释。

`fuzz.WRatio` 是实测选的，`ratio` / `QRatio` 在「无值英雄 → 无职英雄」
这个例子上直接跑偏。三个验证过的用例：

```
无值英雄  → 无职英雄～技能什么的毫无用处～    (90.0)
咒术回站  → 咒术回战
白色相薄2 → 白色相簿2
```

`fuzzy_min_score = 55` 是下限。再低会开始返回明显无关的结果。

## presenter：不重新渲染帖子

搜索结果给的是 `t.me/<username>/<message_id>` 深链，不是重排的帖子内容。

理由在 [ADR-0005](../ADR/0005-permalink-not-rerender.md)：原帖有图、有三个
网盘按钮、有格式，重渲一遍必然不一致，而且要重新处理解压密码和链接失效
问题。一行深链顶掉一整套渲染管线。

`link_mode` 总开关控制深链形式：

| 模式 | 链接 | 谁能看 |
|---|---|---|
| `public`（默认） | `t.me/YXHMd/3665` | 任何人 |
| `internal` | `t.me/c/1702674582/3665` | 仅频道成员 |

## 关键词高亮

用 HTML `<b>` 标签，因为 `parse_mode` 全局设成了 HTML。

高亮必须转义原文再插标签，顺序不能颠倒 —— 先插标签再转义会把 `<b>` 自己
也转义掉。这是 presenter 里唯一容易写错的地方。

## 分页状态存在哪

存在 `callback_data` 里，不在服务端。格式 `s:<page>:<query>`，Telegram 限制
64 字节。

**绝不往 callback_data 里塞 URL** —— 长 URL 必然超限，而且超限的报错发生在
用户点击时，不是发送时，很难复现。见 [ADR-0005](../ADR/0005-permalink-not-rerender.md)。

## 什么时候这个设计会失效

帖子数量到 ~50000 时，LIKE 全表扫会到 100ms 量级，需要换倒排索引
（jieba 分词 + FTS5，或者 Meilisearch）。

以每年新增 ~350 个帖子算，那是 100 年后的事。当前 1639 条，涨到 5 万需要的
不是优化，是另一个频道。
