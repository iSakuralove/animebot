# search —— 检索与展示

四个文件：

| 文件 | 负责 |
|---|---|
| [service.py](../../src/animebot/search/service.py) | 出结果：查库、打分、分页 |
| [presenter.py](../../src/animebot/search/presenter.py) | 排版：文本 + 键盘 |
| [highlight.py](../../src/animebot/search/highlight.py) | 关键词高亮 |
| [callbacks.py](../../src/animebot/search/callbacks.py) | 分页按钮的 callback_data 编解码 |

`service` / `presenter` 分开是因为「怎么算相关性」和「怎么显示」变化频率完全
不同 —— 前者半年不动，后者随时在调。

## 三层管线

```
"#奇幻 无职英雄"
  ↓ Query.parse        拆出 tags=['奇幻'] terms=['无职英雄']
  ↓ 逐词 LIKE 预筛     并集，最多 search_max_candidates 条
  ↓ rank_terms 精排    (命中词数, 匹配质量) 两级排序
  ↓ 标签过滤
  → SearchPage         切片出当前页 + 总数 + 页码
```

预筛用 SQL（快但粗），精排用 Python（慢但准）。

## 为什么必须逐词拆

`/s 无职 转生` 整串 `LIKE '%无职 转生%'` 命中 **0 条** —— 因为帖子里没有
「无职 转生」这个连续子串。逐词拆开后各自命中 1 条和 3 条。

这不是优化，是「多词搜索」这个功能能不能用的前提。

## 分页：每次翻页重新查库

不缓存结果集。一次完整检索实测 12~35ms（最坏是 `#漫改` 572 条全排序 34ms），
而缓存要处理失效、内存增长、以及「翻页时帖子被编辑了」的一致性问题。
省 20ms 不值这些复杂度。

前提是**排序确定**：`sort_key` 是全序，所以重新查得到的顺序完全一致，翻页
不会重复或漏项（`test_no_overlap_or_gap_across_pages` 盯着）。

### `total` 必须是真数

`SearchPage.total` 是过滤后的真实命中数，不是 `len(hits)`。分页之前候选集
上限只影响「少显示几条」；分页之后**总数是用户可见的数字**：

```
#漫改 真实 572 条。cap=200 时界面会显示"共 200 条 / 25 页" —— 那是个谎。
```

所以 `search_max_candidates` 默认调到 3000（> 全库 1639），实测最坏 34ms。
全库涨到 ~5 万时要重新评估，届时该换的是倒排索引而不是继续调大它。

### 页码越界夹回最后一页

不返回空列表。用户点了「末页」之后再点「下一页」，或者按钮是旧的而结果集
变小了 —— 这两种情况都不该看到空白。

### 序号是全局的

第 2 页显示 9~16，正文和按钮一致。用户看到「9」就点「9」，不需要在心里
换算成「本页第 1 条」。

## 翻页按钮：到边界变占位，不移除

```
⏮ ◀ 4/72 ▶ ⏭        中间页
· · 1/14 ▶ ⏭        首页
⏮ ◀ 4/4 · ·         末页
```

移除按钮会让位置在翻页时左右跳动，用户瞄准「下一页」结果点到别的东西 ——
这是最烦人的一类交互 bug。`test_nav_row_width_constant` 断言宽度恒为 5。

占位按钮**必须有 `callback_data`**（用 `NOOP`），否则 Telegram 拒绝整个键盘。
而且 `NOOP` 要注册一个空 handler —— 不 `answer()` 的话客户端一直转圈。

## callback_data 的 64 字节

是**字节**不是字符。一个汉字 3 字节，所以能内联的中文查询词约 19 字。

绝大多数查询远小于这个数（`s:13:少女` 只有 11 字节），所以默认把查询词直接
编进去 —— 无状态、重启不失效、不需要清理。

但超限是真实的，不是假想。库里就有这个标题：

```
英雄王，为了穷尽武道而转生～而后，成为世界最强的见习骑士♀～    30 字 = 90 字节
```

用户直接粘贴标题搜索就会超。超限时退到 `t:<page>:<8位token>` + 进程内 LRU。

`QueryStore` 是有界 LRU（默认 512）。淘汰后用户点翻页看到「搜索已过期，请
重新搜索」—— 可恢复且有明确提示，比静默截断查询词返回错误结果好得多。

这条路径很冷，所以必须有测试盯着，否则等真有人粘贴长标题时才发现。

## 高亮：先定位，再逐段转义

顺序反了两种都错：

- 先转义再插标签 → 要在 `&amp;` 里找关键词，位置全错
- 先插标签再转义 → `<b>` 自己被转义成 `&lt;b&gt;`，用户看到字面标签

另一个坑：**不能用 `text.lower()` 的偏移切原文**。`"İ".lower()` 是 2 个字符
（U+0069 U+0307），偏移会错位。`_fold()` 做逐字符等长小写化，长度变化的字符
原样保留、不参与大小写不敏感匹配。

重叠区间要合并，否则搜 `无职 无职英雄` 会插出 `<b><b>无职</b>英雄</b>`。

标签不参与高亮 —— `#奇幻` 是筛选条件，不出现在标题里，高亮它只在标签行制造
一片粗体噪音。

单条消息最多 40 对标签，防止 `#奇幻` 这类命中几百次把消息撑爆。

## 翻页用编辑，详情用新消息

| 操作 | 方式 | 理由 |
|---|---|---|
| 翻页 | `edit_text` | 发新消息会让聊天记录被同一次搜索的十几个版本刷满 |
| 点详情 | `answer`（新消息） | 用户看完详情还要回去翻页，结果列表要留着 |

编辑的代价是要处理 `"message is not modified"` —— 重复点同一页时 Telegram 报
这个。它不是错误，吞掉；**其它 `TelegramBadRequest` 必须冒泡**到 ErrorBoundary，
两者不能一起吞（`test_other_bad_request_propagates` 盯着）。

## 打分：一个函数取代多路分支

`rank()` 按精确度分层，每层给一个基础分：

| 层级 | 分数 | 例子（查 `无职`） |
|---|---|---|
| `exact` | 1000 | 标题就是「无职」 |
| `prefix` | 900 − 标题长度 | 「无职英雄～技能什么的…」 |
| `title` | 800 − 位置×2 − 长度×0.1 | 「转生成无职的我」 |
| `alias` | 700 − 位置 | 英文名或别名里命中 |
| `body` | 500 | 简介/staff 里命中 |
| `fuzzy` | ≤400 | 错别字容错，见下 |

同层级里减去标题长度和命中位置：**短标题、靠前命中优先**。
「无职英雄」比「某某某无职某某某某某」更可能是用户想要的。

`_FUZZY_SCALE = 4.0` 把 0~100 的 WRatio 映射到 0~400，**天花板压在 `body` 层
之下** —— 任何真实子串匹配都排在模糊匹配之前。这条不能破，否则用户搜到
的第一条是"猜"出来的。

## `sort_key` 为什么是元组

```python
return (-self.hits, -self.score)
```

先比命中词数，再比匹配质量。**不硬压成一个数。**

压成一个数就必须编一个权重（`hits * 10000 + score`），而那个权重是拍脑袋的，
调它等于调一个没人理解的魔数。元组排序的语义是明确的：命中 2 个词的结果
永远排在命中 1 个词的前面，不管分数多少。

## 模糊匹配的触发条件

**只在子串匹配零结果时触发。** 有任何真实命中就不走模糊 —— 模糊结果混进
正常结果里会让排序变得不可解释。

`fuzz.WRatio` 是实测选的，`ratio` / `QRatio` 在「无值英雄 → 无职英雄」
这个例子上直接跑偏。三个验证过的用例：

```
无值英雄  → 无职英雄～技能什么的毫无用处～    (90.0)
咒术回站  → 咒术回战
白色相薄2 → 白色相簿2
```

`fuzzy_min_score = 55` 是下限。再低会开始返回明显无关的结果。

## presenter：不重新渲染帖子

搜索结果给的是 `t.me/<username>/<message_id>` 深链，不是重排的帖子内容。

理由在 [ADR-0005](../ADR/0005-permalink-not-rerender.md)：原帖有图、有三个
网盘按钮、有格式，重渲一遍必然不一致，而且要重新处理解压密码和链接失效
问题。一行深链顶掉一整套渲染管线。

`link_mode` 总开关控制深链形式：

| 模式 | 链接 | 谁能看 |
|---|---|---|
| `public`（默认） | `t.me/YXHMd/3665` | 任何人 |
| `internal` | `t.me/c/1702674582/3665` | 仅频道成员 |

**绝不往 callback_data 里塞 URL** —— 真实数据里的 sharepoint 链接有 200+ 字符，
必然超 64 字节限制，而且报错发生在用户点击时而不是发送时，很难复现。
网盘直链走 URL 按钮，那种按钮不占 callback_data 配额。

## 什么时候这个设计会失效

帖子数量到 ~50000 时会同时撞两面墙：LIKE 全表扫到 100ms 量级，而
`search_max_candidates` 要跟着涨才能保证 `total` 不撒谎，全量排序也变慢。
届时要换的是倒排索引（jieba 分词 + FTS5，或 Meilisearch），不是继续调参数。

以每年新增 ~350 个帖子算，那是 100 年后的事。当前 1639 条，涨到 5 万需要的
不是优化，是另一个频道。
